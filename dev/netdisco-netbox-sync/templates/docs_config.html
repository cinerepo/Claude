How Config works

This page edits rules.yaml — the single file that both Discover (end hosts) and infrastructure sync (switches/firewalls) read to decide VLAN behavior, NetBox tenant/location, and site/role defaults.

VLAN policy fields

Intent
infrastructure — end hosts here auto-promote to NetBox once stable (see Discover docs).
lab / corporate — end hosts become a review candidate instead; nothing auto-pushes.
ignore — never tracked at all (e.g. the default VLAN).
Role / Site
Required. What gets set on any end host promoted from this VLAN if you don't override it manually at promote time.
Tenant / Location
Optional. Applied to end hosts promoted from this VLAN. Leave both blank to omit the field entirely in NetBox rather than setting some placeholder value.

Device overrides — why they're separate from VLAN policy

Site/Tenant/Location for end hosts is VLAN-derived because a host genuinely lives on one VLAN. That doesn't hold for infrastructure devices — a single switch or firewall typically trunks dozens of VLANs, so "which VLAN is this switch's site" has no sensible answer. Device overrides let you set site/tenant/location/role explicitly, keyed by the device's exact name as Netdisco/NetBox report it (case-sensitive, must match exactly). All four are optional — leave any of them blank to fall back to the flat default (site/tenant/location, from .env) or the automatic vendor/model detection (role).

The real bug this exists to fix: NetBox's own device uniqueness is (name, site, tenant) together. If a device's site or tenant is changed manually in the NetBox UI but the sync tool keeps pushing the old value every run, the reconciler can't find a match on that natural key anymore and creates a duplicate device instead of updating the existing one. Setting the override here — so the tool sends the same value every run — is what prevents that. This applies to site exactly the same way it does to tenant; changing an infrastructure device's Site by hand in NetBox directly is not safe without also setting it here.

Role works a little differently — there's no "flat default" for it. Without an override, the role is auto-detected from vendor/model (Fortinet → Firewall, Cisco Catalyst → Switch, Cisco ASR/ISR/CSR/Nexus → Router, everything else → Network Device). That heuristic can't tell a core switch from an access switch, or know about any custom role taxonomy in your NetBox — set the override here any time the auto-detected role isn't the one you actually want.

Validation and safety

Every save follows the same sequence, whether it's a VLAN policy edit or a device override:

  1. Build the updated config in memory.
  2. Write it to a temporary file.
  3. Parse that temp file with the exact same parser sync.py/discover.py use.
  4. If parsing fails, the edit is rejected and shown as an error — rules.yaml is never touched.
  5. If it succeeds, the current rules.yaml is copied to a timestamped .bak file, then the new version replaces it atomically.

IP inventory subnets

Netdisco's IP Inventory report requires an explicit subnet parameter — it won't enumerate "everything." Every CIDR listed here gets queried on each Discovery run to cross-reference MACs already in the staging DB with resolved IPs/hostnames. Anything outside these ranges still gets discovered via MAC/ARP tables, it just stays MAC-only (no IP enrichment). Prefer /18 or /24 ranges — very large ranges (e.g. /8) can make Netdisco time out or return excessive historical records.

Run Sync Now

Runs sync.py for real — the infrastructure pipeline, separate from Discover. For every device Netdisco knows about, it pushes interfaces, IPs, prefixes, VLANs, and learned-MAC data to NetBox via Diode, applying this page's device override (or falling back to the flat default tenant/location in .env) and setting the same discovery_source/last_discovered custom fields the Lifecycle page tracks. Runs every device, every time — this is what keeps an already-synced device's data current, not just new ones.
